# Naranhi — 충돌 위험 평가자 설계 문서 (개발 인계용)

> 이 문서는 기획·설계 단계에서 확정된 내용을 정리한 개발 지침서다.
> Claude Code로 실제 구현을 시작할 때 이 문서를 먼저 읽고 맥락을 파악한다.
> **담당: Tovy(최승현) — 분석 로직 구현 + 검증**

---

## 0. 프로젝트 한눈에

**무엇을 만드나**: 범용 보행 위험 판단 엔진 (오픈소스 라이브러리).
카메라로 들어온 보행 환경에서 장애물을 인식하고, 위험을 판단해 발행한다.
서비스/디바이스가 아니라 **남이 가져다 쓰는 라이브러리** 형태가 핵심.

**대회**: 2026 오픈소스 개발자대회, 자유과제, 일반부문.

**전체 파이프라인**:
```
[트리거] → [인식(YOLO)] → [해석/평가자] → [종합판정] → [발행]
```

**이 문서의 범위**: 위 중 **해석/평가자 — 특히 충돌 위험 평가자** 하나에 집중.
(충돌 평가자만 완성도 있게 구현하고, 낙상·경로 평가자는 확장 지점으로 문서화만.)

**팀 역할 분담**:
- 인식(YOLO ONNX 런타임): 다른 개발자
- 프레임 매칭(BoT-SORT, tracker_id 부여): 다른 개발자
- **분석/평가 로직 + 검증: Tovy(본인)**

## 1. 개발 우선순위 & 전략

- **기능 구현 우선.** 전체 구조를 완벽히 다듬기보다 충돌 평가자가 실제로 동작하는 걸 우선.
- **모바일 우선 → JavaScript로 분석 로직 구현.** 동일한 입출력 계약으로 플랫폼을 확장.
- **입력은 이미 해결된 것으로 전제.** 인식(YOLO)과 매칭(BoT-SORT, tracker_id)은 타 개발자 담당이므로, 본인 로직은 "박스 + 클래스 + confidence + tracker_id가 이미 주어진다"고 가정하고 시작.
- **BoT-SORT가 카메라 모션 보상(CMC)을 포함**하므로, 카메라 움직임으로 인한 매칭 문제는 트래커가 처리한다고 신뢰하고, 로직은 tracker_id를 받아쓴다.

## 2. 데이터 포맷 (포맷① — 인식/매칭 → 평가자)

> 인식 모듈(`nrh-detector 0.10.0`)이 실제로 넘겨주는 값과 연결 완료.
> 변환은 `src/adapters/nrhDetector.js` 한 파일에서만 한다 — 평가 로직은 포맷①만 안다.

### 인식 모듈 출력 ↔ 포맷① 매핑

| 포맷① | nrh-detector | 비고 |
|---|---|---|
| `frame_id` | `image.stream.frame_index` | 스트림이 아니면(단일 이미지) **null** |
| `timestamp` (초) | `image.stream.timestamp_ms / 1000` | **카메라는 항상 null** → `image.received_at` 사용 |
| `frame_size` | `image.width` / `image.height` | 원본 이미지 기준 (레터박스 아님) |
| `tracker_id` | `track_id` | 추적 미확정이면 **null** (실측 3.8%) |
| `class_name` | `class_name` | 이름 그대로. **`class_id`는 쓰지 말 것** — 클래스 병합으로 번호가 밀렸다 |
| `confidence` | `confidence` | 그대로 |
| `bbox {x,y,w,h}` | `{x1, y1, width, height}` | width/height를 이미 파생해 주므로 계산 불필요 |

**시간축이 소스에 따라 다르다.** 영상 파일은 `stream.timestamp_ms`(0부터 시작), 카메라는 그게 항상
null이라 `received_at`(unix epoch)을 쓴다. 어댑터가 데이터를 보고 자동으로 고르고, `source` 옵션으로
검증할 수 있다(`"video"`인데 timestamp_ms가 없으면 throw). **영상 파일에 `received_at`을 쓰면 안 된다** —
그건 처리 시각이라 재생 속도가 아니라 처리 속도를 재게 된다(실측 1.39배 차이 → τ가 그만큼 틀어짐).

```json
{
  "frame_id": 1024,
  "timestamp": 34.13,
  "frame_size": { "width": 640, "height": 480 },
  "objects": [
    {
      "tracker_id": 3,
      "class_name": "kickboard",
      "confidence": 0.87,
      "bbox": { "x": 210, "y": 300, "w": 120, "h": 90 }
    }
  ]
}
```

- `tracker_id`: BoT-SORT가 부여. 프레임 간 동일 객체 식별의 열쇠. τ·예측경로·persistence 계산의 전제.
- `bbox`: 좌상단 (x,y) + 너비/높이 (w,h). 픽셀 단위.
- `class_name`: 표준 클래스명 (인식 담당이 YOLO 인덱스 → 표준명 매핑).
- `frame_size`: **실제 카메라 해상도를 그대로 넘긴다** (팀 결정). 평가 로직은 이 값을 매 프레임 입력으로 받아 전부 비율로 계산하므로 **해상도에 무관하게 동작한다.** 해상도 의존이 남아 있던 유일한 지점(`minRateOfChange`)은 `maxTau`로 교체해 해소했다 (STEP 2 참고).
  - `config/camera.js`의 `CAMERA`는 **엔진이 쓰지 않는다.** 샘플 시나리오 생성·뷰어 초기 캔버스·벤치마크가 참조하는 **기준 해상도**일 뿐이다. 혼동 주의.

## 3. 충돌 위험 평가자 — 핵심 로직 (9단계)

### 설계 철학 (팀 설득/발표용 근거)
- **τ(TTC) 이론** (Lee, 1976): 거리·속도 절대값 없이 "박스 확장률"만으로 충돌까지 시간 추정. 곤충·조류의 충돌 회피 원리.
- **곱셈 게이트** (FMEA 위험평가): 필수조건(경로·신뢰성)이 하나라도 무너지면 전체 위험도가 낮아지는 구조. "위험 = 가능성 × 심각도"의 산업 표준 구조.
- **예측형 경로** (항해 CBDR 원칙): "방위 일정 + 거리 감소 = 충돌". 지금 위치가 아니라 τ초 후 위치로 경로 침범을 판단.

### STEP 0 — 입력
`bbox, class_name, confidence, tracker_id, frame_id` (포맷① 참조)

### STEP 1 — 프레임 간 매칭
**BoT-SORT의 tracker_id를 그대로 사용.** (본인 로직에서 매칭을 직접 구현하지 않음. 이전의 "느슨한 매칭/IOU" 계획은 폐기됨.)

**상태 관리 방식 (결정)**: 평가자는 **무상태(stateless)**로 설계한다. τ·persistence·예측경로 계산에 필요한 tracker_id별 최근 N프레임 히스토리는 평가자 내부가 아니라 **호출자(파이프라인)가 관리**해서 매 호출 시 인자로 전달한다.
- 이유: 같은 입력 → 같은 출력이 보장돼야 트랙 B에서 "가짜 tracker_id 시나리오 JSON"으로 재현 가능한 테스트를 만들 수 있음.
- 히스토리 배열은 오래된/사라진 tracker_id를 정리(prune)해야 한다. 정리하지 않으면 실시간 카메라 스트림을 장시간 운영할 때 메모리가 계속 증가한다.

**구현된 API 계층 (2계층)**: 무상태 원칙을 지키면서도 실사용이 가능하도록 두 층으로 나눴다.

| 계층 | 함수/클래스 | 상태 | 용도 |
|---|---|---|---|
| 무상태 코어 | `assessFrame({frame, prevFrame, history, config})` | 없음 | 재현 가능한 검증·회귀 테스트 (트랙 B 시나리오 JSON) |
| 상태 래퍼 | `new CollisionAssessor(config).assess(frame)` | 직전 프레임 1개 + 최근 N프레임 tracker_id 목록 | 실시간 파이프라인·데모 |
| 객체 단위 | `assessCollisionRisk({objT, objPrev, ...})` | 없음 | 저수준 (보통 직접 쓸 일 없음) |

- 래퍼가 보관하는 상태는 크기가 고정이라 **장시간 돌려도 메모리가 늘지 않는다** — 위에서 말한 prune 문제를 라이브러리가 해결해 준다.
- `assessFrame`이 tracker_id로 이전 프레임 객체를 직접 매칭하므로, 호출자가 서로 다른 객체를 잘못 짝지을 여지가 없다. (저수준 API를 직접 쓸 때는 tracker_id 불일치를 검사해 throw한다.)
- **history 계약**: `assessFrame`에 넘기는 `history`는 **이전 프레임들의** tracker_id 목록이며, 현재 프레임은 함수가 알아서 붙인다. 이렇게 해야 완벽하게 추적된 객체의 persistence가 1.0에 도달할 수 있다(미포함이면 (N-1)/N에서 막혀 reliability 상한이 낮아진다).

### STEP 2 — τ (TTC) 계산
```
τ = bbox_size(t) / ( Δbbox_size / Δt )

# 높이 기준: τ = height(t) / ((height(t) - height(t-1)) / Δt)
# 면적 기준: τ = 2 × rel_area(t) / (Δrel_area / Δt)   ← 면적은 크기의 제곱이라 ×2 보정
```
- **구현은 높이 기준을 채택했다.** 면적 기준과는 종횡비가 고정이고 연속시간일 때만 일치하며, 옆이 가려져 종횡비가 변하면 크게 어긋난다 (9-2 참고).
- `Δt`는 프레임 간 실제 시간 간격 (이벤트 기반이라 매번 다를 수 있음 → 고정값 금지, 실측).
- **Δt 출처 (결정)**: 포맷①의 `timestamp` 필드 차이로 계산한다. `Δt = timestamp(t) - timestamp(t-1)`. 별도의 시스템/브라우저 시각을 쓰지 않는다.
- **예외처리**: STEP 1 매칭 실패(신규 객체) 또는 **|τ|가 `maxTau`를 초과** → τ 대신 **크기 기반 거리 구간(near/mid/far)** 임시 대체. 이 대체값을 risk_from_ttc로 바꾸는 방법은 STEP 3 참고.

- **노이즈 판정 기준 (결정)**: `|τ| > config/ttc.js의 maxTau`(기본 8초)면 τ를 버린다. 크기 변화가 없으면 `rate=0`이라 `τ=Infinity`가 되어 자연히 걸린다.

  초기 구현은 `|Δh/Δt| < 0.5 px/s`로 걸렀는데 **픽셀 절대값이라 두 가지 문제가 있었다.** ① 해상도가 바뀌면 같은 상황이 다르게 판정됨 ② 객체 크기에 따라 다르게 작동(작은 객체엔 관대, 큰 객체엔 엄격). 실제로 10fps에서 박스가 **1픽셀만 흔들려도 10px/s**가 나와 임계값을 가볍게 넘었고, 정지한 큰 물체의 등급이 깜빡였다(risk_from_ttc가 0.7 ↔ 0을 오감).

  `|τ| > maxTau`는 수학적으로 `|rate| < h / maxTau`와 동등하므로 **객체 크기에 비례하는 임계값**이 되고, τ = h/rate는 h와 rate가 함께 스케일되어 **해상도와 무관**하다(실측: 640×480과 1920×1440에서 τ가 동일). 덤으로 τ에 상한이 생겨 예측 위치가 화면 밖으로 폭주하는 문제도 사라졌다.

  **남은 한계**: 작은 객체의 흔들림은 못 잡는다. h=40px에 1px 흔들리면 τ≈4초라 정상 범위처럼 보인다. 다만 그때는 sigmoid 출력이 ≈0이고 폴백값도 far(0.15)라 깜빡임 진폭이 작다. 큰 진폭 깜빡임은 항상 큰 객체에서 나오고 그건 잡힌다. 근본 해결(bbox 이동평균)은 무상태 설계를 깨야 하므로 미뤄뒀다 — 9-2 참고.
- **음수 τ 처리 (결정)**: 박스가 작아지는 중(=객체가 멀어지는 중)이면 τ가 음수로 나온다. 이 경우 충돌 위험이 없는 것으로 간주하고 STEP 3에서 risk_from_ttc를 0에 가깝게 강제한다.
- **주의**: 매칭 신뢰도가 낮으면 예외처리로 넘겨 τ 오염 방지.
- (확장 지점) 디텍션 노이즈로 τ가 급변하는 문제는 이번 버전 범위 밖 — bbox 크기 변화량에 짧은 이동평균을 적용하는 안을 7장에 기록.

### STEP 3 — risk_from_ttc = sigmoid(τ)
τ가 작을수록 급격히 1에 가깝게, 클수록 완만하게 0에 가깝게 (비선형).
- **변곡점·기울기 파라미터는 미확정** → 도구 2(sigmoid 조절기)로 팀 합의하에 튜닝 예정.
- **부호 주의 (결정)**: 표준 sigmoid(x)=1/(1+e^-x)는 x가 클수록 1에 가까워지는 증가함수라 위 규칙과 반대다. 반드시 τ에 대해 **감소함수**가 되도록 구현한다. 실제 구현은 `1 / (1 + exp(k × (τ - τ0)))` 형태이며 `τ0`에서 정확히 0.5가 된다 (`config/sigmoid.js`).
- **음수 τ**: STEP 2 규칙에 따라 risk_from_ttc를 **0으로** 강제한다 (멀어지는 중이므로 안전). sigmoid를 타지 않는다.
- **예외처리 경로 매핑 (결정)**: τ 계산이 불가해 near/mid/far로 대체된 경우는 sigmoid를 타지 않고, 아래 표로 직접 위험도를 매핑한다.

  | 구간 | risk_from_ttc |
  |---|---|
  | near | 0.7 |
  | mid | 0.4 |
  | far | 0.15 |

  (초안 — 실측 데이터로 튜닝 예정, 7장 미확정 목록 참고)

### STEP 4 — 신뢰성 게이트
```
reliability_factor = confidence × detection_persistence_score
```
- `detection_persistence_score` = **최근 T초 안에 탐지된 비율** (`config/persistence.js`)
  - 비율 방식 채택 이유: 카메라 움직임 환경에서 "잠깐 놓침"에 강건. 신규 객체는 자연히 낮은 값(오탐 필터 겸함).
  - **프레임 수가 아니라 시간으로 센다 (결정)**: 인식 fps가 고정이 아니다. 인계 문서 실측으로
    폰에서 켠 직후 12fps, 2분 뒤 5.7fps, 실외 보행 시 3~4fps까지 내려간다. 프레임 수로 창을 잡으면
    같은 N=5가 12fps에서 0.42초, 4fps에서 1.25초를 뜻해 **같은 세션 안에서도 의미가 3배 요동친다.**
  - **분모는 "창이 꽉 찼다면 프레임이 몇 개였을까"**다. 관측된 프레임 간격으로 추정한다.
    실제 프레임 수를 그대로 쓰면 스트림이 막 시작돼 이력이 2~3개뿐일 때 곧바로 1.0이 되어
    오탐 억제가 무력화되고, 고정 프레임 수를 하한으로 두면 fps에 따라 의미가 달라져
    시간 기반으로 바꾼 이유가 없어진다(59fps에서 3프레임은 0.05초뿐이다).
    간격을 추정할 수 없을 때(프레임 1개)만 `minFrames`를 쓴다.
  - `tracker_id`가 null이면 과거를 물을 수 없으므로 "이번에 한 번 보인 것" = 1/분모로 계산한다.

### STEP 5 — 예측형 경로 게이트
```
lateral_velocity = (cx(t) - cx(t-1)) / Δt
predicted_cx = cx(t) + lateral_velocity × τ
path_gate = predicted_cx(및 밑변중심)이 "고정 사다리꼴 경로" 안에 있는 정도
```
- **경로 영역 = 고정 사다리꼴** (카메라 정면 전제, 단순 시작).
- 판정 기준 = **박스 밑변 중심점** (발이 닿는 지점)이 사다리꼴 안인가.
- 현재는 안/밖 이진(binary)으로 시작. 껌뻑임 관찰되면 경계 완충(soft) 추가.
- 사다리꼴 좌표는 **config로 분리** (해상도 대비 비율, 확장 시 로봇용 프로파일 대비).
- **함수 통일 (결정)**: 경로 판정은 하나의 코어 함수 `calcPathGate(point, pixelTrapezoid)`(`src/factors/trackA.js`)로 둔다. 트랙 A(단일 프레임, 매칭 불필요)는 **현재 밑변중심점**을 넣어 호출하고, 트랙 B(연속 프레임)는 `predictivePathGate`가 **예측 밑변중심점**(τ 기반 투영)을 만들어 같은 함수에 넣는다. 검증 뷰어도 이 함수를 그대로 쓴다.
- 설정의 사다리꼴은 비율(%)이므로 `getPixelTrapezoid(config.trapezoid, frameSize)`로 픽셀 좌표로 바꾼 뒤 넘긴다.
- **현재 위치 기준으로 자동 대체하는 경우** (예측 투영이 불가하거나 무의미한 상황):
  - τ가 없음 (신규 객체이거나 변화율이 노이즈 수준)
  - **τ ≤ 0 (멀어지는 중)** — 음수 τ를 그대로 투영하면 시간을 거꾸로 돌려 "객체가 왔던 자리"를 예측 위치로 찍게 된다. 실측으로 확인된 문제라 명시적으로 막는다.
  - 이전 프레임이 없거나 Δt가 비정상

### STEP 6 — 클래스 위험 계수
```
class_weight = config/classes.js 에서 조회 (미등록이면 DEFAULT_CLASS_WEIGHT = 0.5)
```
- 최댓값은 반드시 1.0이어야 한다 — 4장의 앵커 규칙 참고.

### STEP 7 — 최종 결합 (곱셈 + 최솟값 보정)
```js
path_gate = Math.max(path_gate, 0.05)
reliability_factor = Math.max(reliability_factor, 0.05)

risk_score = risk_from_ttc * class_weight * path_gate * reliability_factor
```
- floor(0.05) 이유: 곱셈의 "약한 고리" 방어. 추정 오차 하나로 진짜 위험을 완전히 놓치지 않게.
- floor는 `path_gate`와 `reliability_factor`에만 적용한다. `risk_from_ttc`와 `class_weight`는 0까지 내려갈 수 있다.
- **출력 `factors`에는 floor를 적용한 뒤의 값을 기록한다** → `factors` 네 값을 그대로 곱하면 `risk_score`가 재현된다. 디버깅 때 숫자를 검산할 수 있게 하기 위한 불변식.

### STEP 8 — 등급 변환
```
0.0~0.3 safe / 0.3~0.6 caution / 0.6~0.85 warning / 0.85~1.0 danger
```
- 경계값은 아래쪽 등급에 포함된다 (`risk_score <= 0.3`이면 safe, `<= 0.6`이면 caution, ...).
- 경계값은 `config/riskLevels.js`에 있다.

### STEP 9 — 출력 (포맷② — 평가자 → 종합판정)
```json
{
  "frame_id": 1024,
  "assessor": "collision",
  "tracker_id": 3,
  "risk_score": 0.78,
  "risk_level": "warning",
  "factors": {
    "tau": 1.2,
    "risk_from_ttc": 0.81,
    "class_weight": 1.0,
    "path_gate": 1,
    "reliability_factor": 0.92
  }
}
```
- `factors`에 각 단계 값 기록 → "왜 이 경보가 나왔는지" 설명 가능 + 디버깅/튜닝.
- **`factors.tau`는 `null`일 수 있다** — τ 계산이 불가해 예외처리 경로(거리 구간 폴백)를 탄 경우다. 이때 `risk_from_ttc`는 sigmoid가 아니라 STEP 3의 near/mid/far 매핑표에서 온 값이다.
- `factors` 네 값(`risk_from_ttc × class_weight × path_gate × reliability_factor`)을 곱하면 `risk_score`와 정확히 일치한다 (STEP 7 참고).

## 4. 클래스 목록 & 위험 계수 (초안 — 조정 가능)

**클래스 목록은 인식 모듈 정의(24개)를 그대로 따른다.** 임의로 이름을 바꾸면 매칭이 안 된다.

| class_weight | class_name | 성격 |
|---|---|---|
| **1.0** | `micromobility`, `motorcycle` | 이동체, 빠름, 예측 어려움 |
| 0.8 | `car`, `bus`, `truck` | 크고 정지해도 위험 |
| 0.6 | `person`, `wheelchair` | 흔하나 서로 피할 수 있음 |
| 0.5 | `pet`, `push_cart` | 느린 이동체 |
| 0.4 | `barricade`, `movable_signage`, `bollard`, `pole`, `tree_trunk` | 경로를 막는 정적 장애물 |
| 0.3 | `bench`, `chair`, `table`, `fire hydrant`, `service_terminal`, `control_cabinet`, `transit_stop`, `potted plant`, `traffic light`, `traffic_sign` | 보통 경로 밖이거나 공중 |

> ⚠️ **킥보드와 자전거를 구분할 수 없다.** 모델이 둘을 `micromobility` 하나로 병합해 학습했다.
> 설계 초기에 킥보드를 "한국 특화 최고 위험"으로 따로 뒀지만 모델 수준에서 나눌 방법이 없다.
> 두 클래스 중 위험한 쪽(킥보드) 기준으로 1.0을 줬다.

> ⚠️ **`class_id`(숫자)를 코드에 박지 말 것.** 원본 29개에서 24개로 병합하며 번호가 밀렸고,
> 인식 담당도 이걸로 크게 헤맸다(29개 라벨로 채점했다가 mAP 0.09가 나옴). 항상 `class_name`을 쓴다.

- 값은 감으로 잡은 시작점. AI Hub "인도 보행 영상" 데이터로 실측하며 조정.
- **`config/classes.js`로 분리** (코드 수정 없이 튜닝. 원래 YAML로 계획했으나 파서 의존성을 피하려고 JS 모듈로 바꿨다 — 9-1 참고).
- **미등록 클래스 (결정)**: 목록에 없는 class_name이 들어오면 기본값 **0.5**를 사용한다. `config/classes.js`가 `DEFAULT_CLASS_WEIGHT`로 export한다.

### ⚠️ 앵커 규칙 — 최고 위험 클래스는 반드시 1.0

`risk_score`는 네 요인의 **곱**이므로 **class_weight의 최댓값이 곧 risk_score의 상한**이 된다.
초기 구현에서 최댓값을 0.9로 뒀더니 이론상 최대 risk_score가 0.9에 묶여서, danger 경계(0.85)에
confidence가 거의 1.0일 때만 닿는 문제가 실측으로 확인됐다 (confidence 0.95면 최악의 상황에서도
warning에 머묾). 그래서 kickboard/motorcycle을 1.0으로 올렸다.

**class_weight를 실측 튜닝할 때도 최댓값 1.0은 유지할 것.** 이 규칙은 `test/trackA.test.js`에서
검사한다. class_weight는 "최고 위험 클래스 대비 상대값"으로 해석한다.

## 5. 검증 전략

### 정답 데이터 부재 → 정성 검증 중심
정량 ground truth가 없으므로, **각 STEP을 눈에 보이게 만들어 사람이 판단**하는 방식.
팀원 4명이 같은 영상을 독립적으로 "위험/안전" 표시 → 합의를 유사 정답으로 사용.

### 두 트랙 동시 진행
- **트랙 A (단일 프레임, 매칭 불필요)**: class_weight, confidence, 현재 경로 게이트, 거리구간(near/mid/far). → **도구 1로 검증.**
- **트랙 B (연속 프레임, 매칭 필요)**: τ, 예측 경로, persistence. BoT-SORT 미완성이므로 **가짜 tracker_id 시나리오(JSON)로 선개발**, 나중에 실제 트래커로 교체.

### 검증 도구 3종
1. **단일 프레임 오버레이 뷰어** (JS/웹) — **구현 완료** (single_frame_viewer.html). 이미지 위/빈 배경에 박스·라벨·사다리꼴·밑변중심점·거리구간 표시. **`src/`의 실제 엔진 코드를 그대로 import**하므로 config를 튜닝하면 뷰어에 즉시 반영된다. ES module을 쓰므로 `file://`로 열 수 없고 `npm run viewer`로 실행한다(Node 내장 모듈만 쓰는 정적 서버, 의존성 0개).
2. **통합 튜닝 도구** (JS/웹) — **구현 완료** (`tuner.html`). 원래 계획은 sigmoid 조절기 하나였는데 **모든 파라미터를 한 화면에서 튜닝**하도록 확장했다.
   - τ→위험도 곡선 그래프 + 등급 경계선 + `maxTau` 표시 (`riskFromTau()`를 직접 호출해 그림)
   - **시나리오 영향 표**: 값을 바꾸면 샘플 7종의 프레임별 등급이 즉시 갱신되고, 기본값과 달라진 시나리오는 노란색으로 강조 → "이 값을 바꾸면 무엇이 바뀌는지"를 바로 볼 수 있다
   - 전 파라미터 컨트롤 (클래스 가중치·사다리꼴·sigmoid·등급 경계·폴백·maxTau·N·거리 임계값·기준 해상도)
   - **"적용 방법" 탭**: 기본값과 diff해서 **바꾼 값만** `파일 / 상수·키 / 기존값 → 새 값` 표로 보여주고 붙여넣을 코드까지 생성. 매핑은 `src/configRegistry.js`가 단일 출처이며, config 파일을 추가하면 `test/configRegistry.test.js`가 등록 누락을 잡는다
   - 잘못된 조합(사다리꼴 좌우 역전, 등급 경계 순서 등)은 `loadConfig()`가 throw하고 그 메시지를 그대로 표시한다
   - 파일을 자동 수정하지는 않는다 (브라우저에서 파일 쓰기는 dev 서버 엔드포인트가 필요하고, 필요한 건 "어디를 고칠지 안내"였다)
3. **연속 프레임 재생 뷰어** (JS/웹) — **구현 완료** (`frame_sequence_viewer.html`). tracker_id·등급별 색상, τ 실시간, 예외처리(n/a) 표시, 현재점→예측점 연결선, 요인별 막대와 최종 risk. 프레임 스텝 이동(◀▶ 버튼·슬라이더·좌우 화살표키)과 자동 재생 지원. BoT-SORT를 기다리지 않고 **가짜 tracker_id 시나리오**(`samples/scenarios.js`) 7종으로 선개발했다.
   - **용어 설명 탭** 포함 — 로직을 모르는 팀원에게 τ·path_gate·reliability 등을 그 자리에서 설명할 수 있다.
   - **데이터 탭** — 현재 프레임의 포맷① 입력과 포맷② 출력 원본 JSON.

### 샘플 시나리오 (`samples/scenarios.js`)

각 시나리오는 로직의 특정 부분 하나를 부각하도록 만들었고, `test/scenarios.test.js`가

## 6. 구현 순서 제안 (Claude Code)

> 진행 상황: **1~8번 전부 완료** (2026-08-02). 검증 도구 3종 모두 구현됐다.
> 실행: `npm test`(회귀 테스트 103개), `npm run demo`(터미널 데모), `npm run bench`(성능 측정), `npm run viewer`(검증 뷰어 3종).

1. ✅ **포맷 스키마 정의** — 포맷①②를 코드로 (JS 우선). 생성 시 검증 포함.
   - raw 필드명이 바뀔 것에 대비해 변환을 `src/adapters/format1.js` 한 곳으로 몰았다. 실제 YOLO/BoT-SORT 필드명이 확정되면 이 파일만 고치면 되고 검증 로직은 안 건드린다.
2. ✅ **config 로더** — `config/*.js`(클래스 가중치·사다리꼴·임계값 등)를 병합하고 검증한다. `loadConfig(overrides)`로 일부 값만 덮어쓸 수 있어 튜닝 도구가 이걸 그대로 쓴다.
3. ✅ **단일 프레임 요인 함수들** (트랙 A, `src/factors/trackA.js`):
   - `getClassWeight(class_name)`
   - `classifyDistance(rel_area)` → near/mid/far
   - `calcPathGate(point, trapezoid)` → 밑변중심점(또는 예측점) 판정 (STEP 5 참고, 트랙 A는 현재 밑변중심점을 넘겨 호출)
4. ✅ **sigmoid + 등급 변환** — τ 입력받아 risk_from_ttc, risk_level. (`src/factors/ttcRisk.js`)
5. ✅ **연속 프레임 요인 함수들** (트랙 B, `src/factors/trackB.js`):
   - `estimateTTC(obj_t, obj_prev, dt)` + 예외처리
   - `detectionPersistence(tracker_id, history, N)`
   - `predictivePathGate(obj_t, obj_prev, tau, trapezoid)`
6. ✅ **최종 결합** — STEP 7 곱셈 + floor. (`src/factors/combine.js`)
   - `factors`에는 floor를 **적용한 뒤의** 값을 기록한다 → `factors`를 그대로 곱하면 `risk_score`가 재현되는 불변식이 성립하고, 디버깅 때 숫자를 검산할 수 있다.
7. ✅ **회귀 테스트** — 극단 케이스 고정(정중앙 큰 킥보드=danger / 구석 정지물=safe). 추가로 다음 케이스도 고정:
   - 원거리에서 빠르게 접근 (τ가 핵심적으로 작동해야 하는 케이스)
   - 경로 밖이지만 예측상 곧 진입 (예측 경로 게이트가 핵심적으로 작동해야 하는 케이스)
   - confidence 낮은 오탐 (신뢰성 게이트가 억제해야 하는 케이스)
   - 연속 6프레임 시나리오에서 safe → caution → warning → danger가 순서대로 다 나오는지
   - ⚠️ 테스트에 쓰는 confidence는 **실전에서 나올 법한 값**을 쓸 것. 1.0 같은 값을 쓰면 "위험한데 danger가 안 뜨는" 문제를 테스트가 가려버린다 (실제로 그런 적 있음).
8. ✅ **도구 2, 3 구현** — 튜닝·검증용. 도구 1처럼 **src/를 직접 import**해서 만들었다 (로직을 복제하면 검증 도구가 검증 대상과 다른 코드를 돌리게 됨).
   - 도구 3 (연속 프레임 재생 뷰어) — `frame_sequence_viewer.html`. 예측 위치 같은 중간값은 `src/trace.js`가 계산해서 넘겨준다.
   - 도구 2 (통합 튜닝 도구) — `tuner.html`. `loadConfig(overrides)`로 실시간 반영. 5장 참고.

9. ✅ **성능 계측** (설계 문서에 없던 추가 항목)
   - `src/perf.js` — 프레임 단위 타이밍 수집기. `CollisionAssessor(config, { measure: true })`로 **옵트인**이라 안 쓰면 오버헤드가 0이다.
   - `scripts/benchmark.js` (`npm run bench`) — 객체 수별 평균/p50/p95/최대, 객체당 비용, 추정 최대 FPS, 30fps 예산 대비 비율.
   - **STEP별로 쪼개서 재지 않는다**: 실측에서 성능이 병목이 전혀 아님이 확인됐으므로(7장 참고) 세분화의 실익이 없다. 참고로 타이머 1회 호출이 약 0.043µs, STEP 하나가 약 0.23µs라 STEP별 계측은 값을 약 37% 왜곡한다.

## 7. 확정 안 된 것 (팀 논의 필요)

- 포맷① 최종 합의 (인식·매칭 담당과) — 구조는 현행 유지로 결정됨. 실제 필드명만 확인 필요

- `maxTau` 값 (`config/ttc.js`, 현재 8초) — 실제 디텍션 흔들림 폭을 보고 조정
- bbox 이동평균 도입 여부 — `maxTau`로 큰 객체 흔들림은 잡혔으나 작은 객체는 남아 있다 (STEP 2·9-2 참고). 무상태 설계를 깨야 하므로 필요성이 실측으로 확인된 뒤에 결정

### 9-2. τ 계산의 한계
- **높이 기준만 구현함**: STEP 2는 높이 기준과 면적 기준 두 공식을 제시하지만 구현은 **높이 기준만** 쓴다. 옆이 가려질 때 폭(w)이 흔들려도 높이는 비교적 안정적이라 이쪽이 강건하다.
- **두 공식은 조건부로만 같다**: "면적 기준에 ×2 보정하면 높이 기준과 동일"은 ①종횡비 고정 ②연속시간 극한 두 조건에서만 성립한다. 실측하면 종횡비가 고정이어도 이산 차분 때문에 τ_height=1.100 / τ_area=1.152로 어긋나고, 종횡비가 변하면(옆 가림) τ_height=1.100 / τ_area=**-19.8**까지 벌어진다. 높이 기준 채택이 옳은 선택이었음을 뒷받침.
- ~~**τ가 매우 클 때 예측 위치가 폭주**~~ → **해결됨.** `maxTau`(8초)가 τ에 상한을 두므로 예측 투영 거리도 자연히 제한된다.
- ~~**`minRateOfChange`가 해상도 의존**~~ → **해결됨.** `maxTau`로 교체. τ는 해상도·객체 크기와 무관하다 (STEP 2 참고).
- ~~**탐지 흔들림에 등급이 깜빡임**~~ → **큰 객체는 해결됨.** 1px 흔들림은 τ로 환산하면 20초쯤이라 `maxTau`에 걸린다.
- **작은 객체의 흔들림은 여전히 남아 있다**: h≈40px에 1px 흔들리면 τ≈4초로 정상 범위처럼 보인다. 다만 그때는 sigmoid 출력이 ≈0이고 폴백값도 far(0.15)라 깜빡임 진폭이 작아 실용상 영향이 적다. 근본 해결은 bbox 크기에 이동평균을 적용하는 것인데 **무상태 설계를 깨야 하므로**(tracker별 bbox 히스토리 필요) 필요성이 실측으로 확인된 뒤에 결정한다. 7장 참고.
- **폴백 경로가 sigmoid 경로보다 높은 위험도를 줄 수 있다**: τ가 `maxTau`를 살짝 넘으면 폴백으로 넘어가는데, 큰 물체라면 near=0.7이 된다. 반면 `maxTau` 안쪽이면 sigmoid가 ≈0을 준다. 즉 경계에서 0 ↔ 0.7의 불연속 점프가 생긴다. 설계상 "가까운 큰 물체는 주의 대상"이라는 의도된 동작이지만, 경계 근처에서 튀는 것은 남은 문제다.

### 9-3. 견고성 — 라이브러리 배포 전 정리 완료 (2026-08-04)

동료 개발자에게 테스트용으로 넘기기 전 3라운드 코드 리뷰를 돌려 **13건을 실측으로 확인하고 전부 수정**했다.
공통점은 모두 "조용히 잘못된 결과를 내던" 지점이었다는 것이다. 재발 방지 테스트는 `test/hardening.test.js`에 있다.

| 문제 | 증상 | 수정 |
|---|---|---|
| tracker_id 중복 미검증 | 같은 프레임에 중복 id가 있으면 이전 프레임 매칭이 엉켜 **τ가 조용히 오염**됨 (실측: 첫 객체 τ가 +1.0이어야 할 상황에 -0.2) | `validateDetectionFrame`에서 프레임 내 유일성 검사 후 throw |
| config 오타가 조용히 무시 | `loadConfig({ sigmod: {...} })` (오타)가 아무 말 없이 무시돼 튜닝값이 안 먹는데 알 수 없었음 | 알 수 없는 섹션·키를 throw하고 **쓸 수 있는 이름을 함께 안내**. `classWeights`만 예외(클래스 추가는 정상 사용법) |
| config가 동결 안 됨 | 로드 후 `config.classWeights.kickboard = 5` 같은 직접 대입이 **검증을 우회**해 잘못된 설정으로 돌아감 | `loadConfig` 결과를 깊게 동결(deep freeze). 값을 바꾸려면 `loadConfig(overrides)`로 다시 만든다 |
| `getClassWeight` 프로토타입 노출 | class_name이 `"toString"` 등이면 class_weight가 **함수**가 되어 risk_score가 NaN → 원인 추적 어려운 에러 | `Object.hasOwn()`으로 자기 소유 키만 조회 |
| history 누락이 조용히 억제 | `assessCollisionRisk`에 history를 빼먹으면 persistence=0 → 위험도가 눌려 **"왜 danger가 안 뜨지"** 상황 | 배열이 아니면 이유를 설명하며 throw |
| history 원소가 배열이 아님 | `Cannot read properties of null (reading 'includes')` 원시 에러 | **몇 번째 원소**가 잘못됐는지 알려주며 throw |
| prevFrame 미검증 | bbox에 문자열이 섞인 prevFrame이 통과해 τ가 조용히 오염 (실측: τ=-0.1) | `assessFrame`이 prevFrame도 검증 |
| config 누락 시 원시 에러 | `Cannot read properties of undefined (reading 'thresholds')` | "config가 필요합니다 — loadConfig()의 결과를 넘기세요" |
| 프레임당 파싱 2회 | `CollisionAssessor` → `assessFrame` 경로에서 중복 파싱 | `assessFrameDetailed`가 검증된 프레임을 함께 반환 → 파싱 1회 |
| 패키지에 무관 파일 | `.claude/`와 프로젝트와 무관한 71KB zip이 배포물에 포함 | `files` 화이트리스트 (패키지 132KB → 70KB) |
| `exports`/`engines` 없음 | 서브패스 접근이 우발적으로 열려 있고 Node 버전 요구가 미선언 | `exports`로 공개 경로 명시, `engines: node>=20` |

**리뷰에서 정상 확인된 것** (회귀 방지로 테스트에 고정): 입력 불변성 · 결과 객체 독립성 · 문자열 tracker_id 지원 ·
20000프레임 후에도 상태 크기 고정 · bbox의 NaN/Infinity 차단 · Δt=0/역행 안전 처리 · config 공유 시 상태 격리 ·
해상도 무관 동작(640×480과 1280×960에서 등급 시퀀스 일치).

### 9-5. 첫 실영상 통과에서 나온 것 (2026-08-16)

인식 모듈 샘플 영상(`sidewalk-640.mp4`, 360×640 세로, 59fps, 1173프레임)을 끝까지 통과시킨 결과다.
`npm run dump`으로 재현할 수 있다.

**잘 된 것**
- 파이프라인 전체가 동작한다: 인식 → 어댑터 → 평가 → 포맷② 8506개
- 평가 비용이 **전체 지연의 0.13%** (인식 17.4ms vs 평가 0.013ms). 성능은 논점이 아니다
- `track_id` null 3.8%(323개)가 폴백 경로로 정상 평가됐다 — 버렸다면 그만큼 못 봤을 것

**🔴 사다리꼴이 이 영상에 전혀 안 맞는다 — 최우선 튜닝 대상**
- `path_gate=1`이 8506개 중 **6개(0.1%)**. 나머지는 전부 floor(0.05)로 눌렸다
- 그 결과 **99.98%가 safe**로 나왔다 (caution 1, warning 1, danger 0)
- τ와 reliability는 정상이다(양수 τ p50 0.66초, reliability p50 0.70). **경로 게이트만 문제**
- 원인: 사다리꼴 기본값이 640×480 가로 기준인데 영상은 360×640 세로다
- → 단일 프레임 뷰어에 실제 프레임을 올려 슬라이더로 맞춰야 한다. 회의 안건 "사다리꼴 실측 튜닝"이
  이제 구체적인 숫자를 갖게 됐다

**🟠 고fps에서는 흔들림이 τ를 *작게* 만든다 (새로 발견)**
- 시나리오 7에서 다룬 건 τ가 **크게** 튀는 방향이었고 `maxTau`가 막아준다
- 그런데 59fps에서는 Δt=0.017초라, 박스가 1픽셀만 커져도 rate가 59px/s가 된다.
  h=50px이면 τ=0.85초 — **"임박한 충돌"로 읽힌다**
- `maxTau`는 큰 τ만 거르므로 이 방향은 못 막는다
- 실측 양수 τ 분포가 p05 0.14 / p50 0.66초로 전반적으로 작은 것이 이것 때문일 수 있다
  (진짜 접근인지 흔들림인지는 사다리꼴을 맞춘 뒤 다시 봐야 구분된다)
- 해결 후보: bbox 크기에 이동평균(9-2에 기록된 항목) / 고fps에서 stride를 올려 Δt를 키우기

### 9-6. 사다리꼴이 실제 카메라 구도와 어긋나 있다 (2026-08-16)

실제 보행 영상 4편(1080×1920 세로, 60fps)에서 균등 간격으로 10프레임씩 뽑아
자체 촬영 영상에서 추출한 프레임으로 밑변중심점 분포를 확인했다.

**밑변중심점의 y가 전부 화면 위쪽에 몰려 있다.**

| 영상 | 발점 y (화면 위에서부터 %) |
|---|---|
| 1000022322 | p10 10 / p50 18 / p90 30 |
| 1000022324 | p10 8 / p50 18 / p90 34 |
| 1000022325 | p10 18 / p50 28 / p90 38 |
| 1000022326 | p10 3 / p50 9 / p90 33 |
| sidewalk-640 | p10 10 / p50 28 / p90 42 |

그런데 사다리꼴 기본값은 `topH: 50`이라 **화면 아래쪽 절반만** 덮는다.
객체는 위쪽 절반, 사다리꼴은 아래쪽 절반 — **완전히 어긋나 있어 276개 발점 중 0개가 경로 안**이었다.

**원인은 숫자가 아니라 구도에 대한 가정이다.** 세로로 든 폰에서 화면 하단은 발밑 바닥이라
장애물이 없고, 장애물은 전부 원경(화면 위쪽)에 작게 찍힌다. 경로 사다리꼴은 화면 하단에서
**소실점(화면 상단 근처)까지 뻗어야** 한다 — `topH`가 90 안팎이어야 한다.

`topH`를 올려가며 잰 값 (botL 20 / botR 80 / topL 45 / topR 55 고정):

| topH | 50 | 70 | 80 | 88 | 94 | 99 |
|---|---|---|---|---|---|---|
| 경로 안 | 0.0% | 3.6% | 11.2% | 20.3% | 23.6% | 26.1% |

**주의 — "경로 안 비율 최대화"는 목표가 아니다.** 위변 폭을 20~80까지 넓히면 64.9%까지 오르지만,
그건 경로 게이트를 사실상 꺼버리는 것이다. 게이트의 목적은 "내 길이 아닌 것을 걸러내는 것"이므로,
최종 값은 프레임을 보며 **"이 물체가 실제로 내 진행 경로에 있나"**를 사람이 판단해 정해야 한다.
튜너의 "실측 프레임" 탭이 그 판단을 위한 도구다.

**부수적으로 확인된 것**: 설계 문서 STEP 5의 "카메라 정면 전제"가 실제 구도와 맞는지는
이 작업으로 처음 검증하게 된다. 10장에서 경로 위치가 크게 흔들리면 고정 사다리꼴 가정 자체를
재검토해야 한다 — 폰 기울기 변동이 크다는 뜻이기 때문이다.
